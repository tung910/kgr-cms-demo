# CMS Portal

CMS Portal is a Vite, React, and TypeScript frontend foundation for internal
device operations. It includes a device-management vertical slice, typed API
boundaries, URL-backed filters, role-to-capability authorization, and an
optional MSW-backed local development mode.

## Prerequisites

- Node.js 24 or later
- pnpm 10 or later

## Install and run

Install the pinned dependencies:

```bash
pnpm install
```

Copy the example environment file to a local, ignored file before changing
values:

```bash
cp .env.example .env.local
```

Start the development server:

```bash
pnpm dev
```

## Environment configuration

The application validates its environment at startup. Both variables are
Vite-exposed client configuration, so they must not contain secrets.

| Variable            | Default | Purpose                                                           |
| ------------------- | ------- | ----------------------------------------------------------------- |
| `VITE_API_BASE_URL` | `/api`  | Base URL used by the Axios API client.                            |
| `VITE_ENABLE_MOCKS` | `false` | Enables MSW browser mocks in development only when set to `true`. |

### Mock mode

The included `.env.example` enables the local mock API:

```dotenv
VITE_API_BASE_URL=/api
VITE_ENABLE_MOCKS=true
```

Run `pnpm dev`, then sign in on the login screen with a phone number and
password. In mock mode the screen lists one seeded account per system role;
pick one to fill the form (all use the password in
`src/features/system/mocks/systemFixtures.ts`). Mock API responses are served by MSW only in Vite development
mode. Production builds never start or register the browser mock worker,
regardless of the environment value.

### Real API mode

Point the client at the deployed API and disable browser mocks in `.env.local`:

```dotenv
VITE_API_BASE_URL=https://api.example.internal
VITE_ENABLE_MOCKS=false
```

The API client sends requests relative to `VITE_API_BASE_URL` and validates
device DTOs before UI code consumes them. `httpAuthAdapter` calls the session endpoints (`/auth/login`, `/auth/session`,
`/auth/logout`, `/auth/simulate`), which MSW implements in
`src/features/system/mocks`. Integrating a real identity provider means
supplying another `AuthAdapter` to `AuthProvider` while keeping authorization
enforced by the backend.

## Architecture boundaries

See [Coding Conventions](docs/CODING_CONVENTIONS.md) for the mandatory rules
that apply these boundaries in implementation.

- `src/app` composes application-wide providers, styling, and router setup.
- `src/core` owns cross-cutting configuration, API transport and errors,
  authentication contracts, and capability definitions.
- `src/features` contains vertical feature slices. A feature owns its DTO
  schemas, mapping, API functions, queries, components, and pages.
- `src/routes` defines TanStack Router routes, URL search validation, loaders,
  and route-level access checks. `src/routeTree.gen.ts` is generated by the
  router plugin and remains committed.
- `src/shared` contains reusable presentational components, utilities, and
  cross-feature types without feature-specific API behavior.
- `src/mocks` contains MSW fixtures and handlers used only by development
  startup. `public/mockServiceWorker.js` is the generated static worker and
  remains committed.

Device API responses follow a strict boundary: parse wire DTOs with Zod,
convert snake_case DTOs to feature models in a mapper, then pass only mapped
models to components. List filter and pagination state belongs in validated
route search parameters, not component-local duplicate state.

## Capability conventions

Components, routes, and actions check named capabilities such as
`device.read`, `device.view_owner`, `device.export`, and `device.command`.
They must not branch on role names. The role-to-capability mapping lives in
`src/core/permissions/capabilities.ts`; use `hasCapability` for route and
navigation decisions and `PermissionGuard` for conditional UI.

### Capabilities, role groups and navigation

Role → capability mapping is owned by the backend: at sign-in the session
returns the role's capabilities and `registerRoleCapabilities` makes them
available to `hasCapability`. `ROLE_CAPABILITIES` in
`src/core/permissions/capabilities.ts` only seeds the six system role groups
(the default matrix is documented in that file). Super Admins can add custom
role groups and edit the matrix in **System → Role groups** (M10, SCR-04).

A menu item is visible exactly when the role holds its read capability
(`MENU_CAPABILITY`), so menus cannot drift from capabilities. `overview` is
open to everyone. Hidden menu pages render a forbidden state when opened
directly.

The **System** group (M10) contains Members, Role groups, Audit log and System
settings (parameters, catalogs, backup & restore). Role simulation (Super Admin
only) shows a banner and blocks every write in the API client; the mock backend
rejects writes too. See [CMS_QnA_V1_SPEC](docs/CMS_QnA_V1_SPEC.md) §10 for the
requirements and its final section (_Điểm cần làm rõ với KGR_) for the open
questions.

Client-side checks provide navigation and UX defense in depth. Backend
authorization remains authoritative: every real API endpoint must independently
enforce the authenticated user's permissions and redact data such as owner PII
when appropriate.

## Adding a feature

[SCREEN_WORKFLOW](docs/SCREEN_WORKFLOW.md) is the authoritative step-by-step
checklist — follow it in order:

> Spec → Capabilities → Schema → API/Mapper → Query → Mock → i18n →
> Component/Page → Route → Menu → Verify → Commit

Each step lands in the feature's own slice under `src/features/<name>`, with
routes under `src/routes`. The mandatory rules behind those steps (Zod at the
boundary, capability checks, i18n in both languages, no role-name branching)
live in [Coding Conventions](docs/CODING_CONVENTIONS.md). `src/features/devices`
is the reference slice to copy from.

Automated test tooling is intentionally deferred for this foundation. Do not
introduce a test framework or test files until that work is explicitly planned.
