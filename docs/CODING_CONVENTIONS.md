# Coding Conventions

Rules marked **🔒 Required** block a PR if violated. Rules marked
**💡 Recommended** are defaults you may deviate from with a reason in the PR
description.

## Scope and architecture

The portal is a feature-first modular monolith. Keep application bootstrap,
providers, router configuration, and global styles in `src/app`; cross-cutting
services in `src/core`; feature-neutral UI, types, and helpers in `src/shared`;
and business code in `src/features/<feature>`.

### 🔒 Required

- A feature may use `core` and `shared`; `core` and `shared` must not import a
  business feature.

  _Why: `core`/`shared` must stay reusable across every feature. If they
  depend back on one feature, deleting or refactoring that feature breaks
  unrelated code._

  ```ts
  // ❌ src/core/notifications/toast.ts
  import { deviceStatusLabel } from '@/features/devices/utils';

  // ✅ src/core/notifications/toast.ts — keep it feature-agnostic
  export function showToast(message: string, kind: 'success' | 'error') { ... }
  ```

- Do not edit `src/routeTree.gen.ts`; it is generated by the router plugin.
- Keep TanStack Router route files thin: validate route parameters/search,
  perform route-level guards/loaders, then render a feature-owned page. Do
  not put business logic or data fetching directly in a route file.

### 💡 Recommended

- Prefer the `@/` path alias for cross-module imports. Use relative imports
  only within the same feature slice.

  ```ts
  // Within features/devices/components/DeviceCard.tsx
  import { deviceQueries } from '../queries/device.queries'; // ✅ relative, same feature

  // From features/devices/* referencing shared
  import { PageHeader } from '@/shared/components/PageHeader'; // ✅ alias, cross-module
  ```

## TypeScript, components, and UI

### 🔒 Required

- Strict TypeScript. No `any`, no unsafe type assertions (`as` casting away
  the real type), no untyped API payloads — every payload is parsed by a Zod
  schema (see _Data, API, and server state_).
- Choose either Ant Design `Form` or React Hook Form for a given form — never
  mix both in the same form.
- Do not deeply override Ant Design internals (no targeting `.ant-*` classes
  or DOM structure with custom CSS).

  ```css
  /* ❌ */
  .ant-table-tbody > tr > td {
    padding: 4px;
  }
  ```

  ```tsx
  {
    /* ✅ theme tokens or a wrapper className */
  }
  <ConfigProvider theme={{ token: { colorPrimary: '#1d4ed8' } }}>
    <Table className="devices-table" />
  </ConfigProvider>;
  ```

- Reuse `PageState`, `StatusTag`, `ConnectionStatusBadge`, `RouteErrorState`
  and the `@/shared/components/portal` set (`PortalPageHeader`, `PortalCard`,
  `PortalStatCard`, `PortalBadge`, …) before creating a feature-specific
  equivalent. Search `src/shared/components` first; only add a new shared
  component if none fits, and only add a feature-local one if it is genuinely
  feature-specific.

### 💡 Recommended

- Naming: PascalCase for React components (`DeviceListPage`), camelCase for
  values/functions (`deviceQueries`), descriptive over abbreviated.
- Two-space indentation, single quotes, semicolons — Prettier is the
  source of truth; do not hand-format against it.
- Ant Design for enterprise controls (tables, forms, modals); Tailwind CSS for
  layout, responsive behavior, spacing, and custom presentation.

## Data, API, and server state

### 🔒 Required

- Feature code depends on `ApiClient` only — never import Axios types or an
  Axios instance directly in feature code.
- At the API boundary: define a Zod schema for the wire DTO, parse the raw
  response against it, then map the parsed DTO to a camelCase domain model
  before it reaches any component. Keep mappers pure; preserve missing
  optional data as `null`/`undefined` rather than inventing a default value.

  ```ts
  // features/devices/schemas/device.schema.ts
  export const deviceDtoSchema = z.object({
    id: z.string(),
    owner_name: z.string().nullable(),
    last_seen_at: z.string().nullable(),
  });

  // features/devices/api/get-devices.ts
  export async function getDevices(filters: DeviceFilters) {
    const raw = await apiClient.get('/devices', { params: filters });
    const dtos = deviceDtoSchema.array().parse(raw);
    return dtos.map(toDeviceModel);
  }

  // features/devices/api/device.mapper.ts
  export function toDeviceModel(dto: DeviceDto): Device {
    return {
      id: dto.id,
      ownerName: dto.owner_name, // preserved as null, not defaulted to ''
      lastSeenAt: dto.last_seen_at,
    };
  }
  ```

- File placement: schemas in `features/<feature>/schemas`, API calls and
  mappers in `features/<feature>/api`, TanStack Query option factories in
  `features/<feature>/queries`.
- Components consume query option factories, never hand-written
  `queryKey` arrays. Naming: `<feature>Queries.<action>`, e.g.:

  ```ts
  // features/devices/queries/device.queries.ts
  export const deviceQueries = {
    list: (filters: DeviceFilters) =>
      queryOptions({
        queryKey: ['devices', 'list', filters],
        queryFn: () => getDevices(filters),
      }),
    detail: (id: string) =>
      queryOptions({
        queryKey: ['devices', 'detail', id],
        queryFn: () => getDevice(id),
      }),
  };

  // in a component
  const { data } = useQuery(deviceQueries.list(filters)); // ✅
  const { data } = useQuery({ queryKey: ['devices', filters], queryFn: ... }); // ❌ hand-written key
  ```

- List filters, pagination, and any shareable view state live in validated
  route search parameters, not duplicated component state (`useState`).

## Authorization, privacy, and mocks

### 🔒 Required

- Guard routes, navigation, and actions with named capabilities via
  `hasCapability` or `PermissionGuard`. Never check role names in UI code.

  ```ts
  // ❌
  if (user.role === 'admin') { ... }

  // ✅
  if (hasCapability('device.write')) { ... }
  ```

  _Why: capabilities are the stable contract between frontend and backend;
  role names change or get renamed, capabilities don't._

- Client-side guards improve UX only — the backend must authorize every
  request regardless of what the UI shows or hides.
- Treat owner information as PII: render and export it only when the
  relevant capability _and_ the backend response allow it. Do not fall back
  to showing it "just in case" when a capability check is ambiguous.
- Do not expose secrets via `VITE_*` environment variables. Never commit
  `.env.local`.

### 💡 Recommended

- Keep development-only mocks in `src/mocks` or a feature's own `mocks`
  folder. MSW starts only in development, when `VITE_ENABLE_MOCKS=true`.

## Internationalization (i18n)

The portal uses `react-i18next`. English (`en`) is the default/fallback
language; Vietnamese (`vi`) is a fully maintained secondary language.

### 🔒 Required

- No hardcoded user-facing string in JSX or TS — every label, title, button
  text, and aria-label goes through `useTranslation(<namespace>)` + `t()`
  (or `i18n.t()` outside components, e.g. in `mockAuthAdapter.ts`).
- Namespace = feature folder name. Translations live in
  `src/features/<feature>/locales/{en,vi}.json`. Shared app chrome (nav,
  breadcrumb, roles, topbar, sidebar, `PageState`, login) uses the `common`
  namespace at `src/core/i18n/locales/{en,vi}.json`.
- Every namespace registered in `src/core/i18n/index.ts` must have both an
  `en.json` and a `vi.json` file, even if empty (`{}`) — resources are
  imported statically/eagerly, so a missing file breaks the build.
- Add a key to **both** `en.json` and `vi.json` in the same change; never
  leave a language behind.
- Business/mock data (serial numbers, customer names, city names, phone
  numbers, etc. in `features/*/mocks/*.ts`) stays untranslated. Only extract
  a mock field into locale files when it is actually a static UI label that
  was misplaced in mock data (e.g. a stat-card `label`); the mock keeps just
  the `key`/`id` used to look up the translation.
- Changing the active language must also sync antd (`ConfigProvider locale`)
  and dayjs (`dayjs.locale(lng)`) — use `setLanguage` from
  `src/core/i18n/languagePreference.ts` rather than calling
  `i18n.changeLanguage` directly.

### 💡 Recommended

- Key naming: nest by page/section under the feature namespace, don't repeat
  the feature name in the key (`t('page.title')`, not
  `t('devices.page.title')` inside the `devices` namespace).
- Before adding a new feature slice, `grep -rP '[à-ỹÀ-Ỹ]'` (or any hardcoded
  literal) inside it to confirm nothing was missed.

## Verification

Automated test tooling is intentionally deferred — do not introduce a test
framework or test files without an approved plan.

Before opening a PR, run:

```bash
pnpm lint
pnpm typecheck
pnpm format:check
pnpm build
```

All four must pass before a change is considered done. Manually exercise
affected flows with MSW where applicable, including denied-capability,
loading, empty, and error states.
